# Дашборд трат: отдельный фронтенд на React и API на django-ninja

Дата: 2026-10-24
Статус: на согласовании у владельца (проверка исполнителем пройдена)

## Зачем

Хочется каждый день открывать одну страницу и за пять секунд понять две вещи: сколько потрачено и можно ли верить этим цифрам. Сейчас главная `/money/` пустая заглушка, а траты видны только в админке.

Транзакции попадают в систему из банковских выписок. Автоматически приходит только BCC, и эта загрузка сейчас сломана, остальные банки загружаются вручную. Поэтому дашборд должен честно показывать, на какую дату актуальны данные по каждому банку, а не только суммы.

Вторая причина: владелец хочет освоить современный фронтенд-стек на своём проекте (React для него в новинку) и держать фронтенд отдельно от бэкенда. Отсюда отдельное SPA, а не Django-шаблон.

## Цели

- Главный экран (раскладка «A, цифры сверху», выбрана по макетам):
  1. Три суммы трат: **сегодня**, **текущая неделя**, **текущий месяц**. У месяца подпись со сравнением с прошлым месяцем на ту же дату (например, «↑ 8% к сентябрю»).
  2. Строка статусов: свежесть данных по каждому банку, свежесть курсов валют, число трат без категории. Цвет: зелёный / оранжевый / красный.
  3. График трат по категориям: горизонтальные полосы, переключатель «Неделя / Месяц», отдельная серая полоса «Без категории».
  4. Последние транзакции за сегодня и вчера, сгруппированные по дням.
- Переключатель валюты в шапке. По умолчанию **AUD**. При переключении пересчитывается всё: три суммы, график и суммы в списке транзакций.
- Нормальный вид на телефоне: блоки встают в одну колонку.
- Отдельный фронтенд (React + TypeScript + Vite) поверх API на django-ninja. Это задел под следующие экраны.

## Не цели (в этой версии)

- **Блок остатка на счетах.** `Account.balance` сейчас никто не обновляет. Остатки появятся после отдельного проекта, где баланс сохраняется из выписок. Место под блок в раскладке не резервируем.
- **Автоматическая загрузка выписок** и починка BCC. Это отдельный проект.
- Редактирование транзакций и категорий, загрузка выписок из нового фронта. Для этого остаются старые страницы и админка.
- Кешбэк (`TransactionCashback`) и доходы в суммах.
- Многопользовательский доступ и общий доступ к дашборду.
- Перевод интерфейса на другие языки. Интерфейс только на русском.

## Анти-цели (провал, даже если «работает»)

- **Цифры молча врут:**
  - устаревшие данные выглядят как свежие;
  - суммы в разных валютах складываются без пересчёта;
  - переводы между своими счетами считаются тратами;
  - транзакции без курса тихо пропадают из сумм.
- Сломаны существующие страницы: загрузка выписок, загрузка курсов, админка, вход, API для внешней загрузки (`/money/api/...`).
- На VM появляются новые долгоживущие сервисы. Node нужен только на этапе сборки.
- Код фронта переусложнён. Владелец учит React на этом проекте, поэтому код должен быть обычным, идиоматичным и читаемым, без хитрых абстракций.

## Решения владельца

- Фронтенд: **React + TypeScript + Vite**.
- Бэкенд API: **django-ninja**.
- Раскладка: вариант **A** из макетов (`.superpowers/brainstorm/`, файл `layout.html`).
- Валюта по умолчанию **AUD**, с переключателем; пересчитывается всё.
- Порядок проектов: сначала дашборд, потом остатки, потом автоматические выгрузки.
- Переводы между своими счетами исключаются **флагом на категории**. У категории есть признак «не трата»; транзакции с такой категорией в суммы не попадают. Размечаются они правилами (`PlaceCategoryMapping`) или вручную.

## Решения, которые принял я (владелец может поправить)

### Стек фронта
- SPA без серверного рендеринга (не Next.js): дашборд за логином, SSR ничего не даёт, а Node-сервер в проде не нужен.
- **Tailwind CSS + shadcn/ui** для вёрстки и компонентов, **TanStack Query** для запросов, **Recharts** для графиков.
- Типы API генерируются из OpenAPI-схемы django-ninja через `openapi-typescript`. Сгенерированный файл коммитится, команда `npm run gen:api`.
- Node 22 LTS, npm. Код в `frontend/` в этом же репозитории.
- Тесты фронта: Vitest + React Testing Library. Минимум: пересчёт и форматирование сумм, раскраска статусов, рендер главного экрана на моковых данных.

### Где что живёт по URL
- SPA отдаётся с корня `/`. Сейчас `/` редиректит на `/money/`, этот редирект убираем.
- Django продолжает отвечать на `/admin/`, `/accounts/`, `/money/` (старые страницы остаются), `/static/` и новый `/api/`.
- Вход через существующий логин Django (`/accounts/login/`). Если API отвечает 401, SPA отправляет на `/accounts/login/?next=/`. После входа Django возвращает на `/`, то есть в SPA. Для этого `LOGIN_REDIRECT_URL = '/'` уже стоит.
- Аутентификация через сессионную cookie Django. Фронт и API на одном домене, поэтому CORS и токены не нужны. API первой версии только читает (GET), но CSRF оставляем включённым по умолчанию ninja на будущее.

### API (`/api/`, django-ninja)
Все эндпоинты требуют входа и отдают данные только текущего пользователя.

- `GET /api/me`: имя пользователя, валюта по умолчанию, список доступных валют.
- `GET /api/dashboard/summary?currency=AUD`: суммы трат за сегодня, неделю и месяц, сумма прошлого месяца на ту же дату, число транзакций без курса.
- `GET /api/dashboard/categories?period=week|month&currency=AUD`: траты по категориям верхнего уровня плюс «Без категории».
- `GET /api/dashboard/transactions/recent?currency=AUD`: траты за сегодня и вчера (тот же отбор, что и для сумм). По каждой: дата, место или комментарий, категория, сумма в выбранной валюте, исходная сумма и валюта транзакции.
- `GET /api/dashboard/status`: свежесть по счетам, дата последнего курса, число трат без категории, число выписок в статусах FAILED и зависших PENDING.

Отдельный эндпоинт на каждый блок, чтобы блоки грузились и падали независимо, а переключение периода у графика перезапрашивало только график.

### Как считаются цифры
- **Трата**: транзакция с `transaction_type='expense'` текущего пользователя, у которой категория не помечена «не трата» (см. «Изменение модели» ниже). Транзакции без категории считаются тратами. Сумма трат равна сумме `abs(amount)`. Расходы в базе обычно хранятся отрицательными (так пишут парсеры CommBank и BCC), но встречаются и положительные, например комиссия FF `+30`. Они тоже увеличивают траты. Переводы (`transfer`) и доходы (`income`) не входят. Возвраты приходят как `income` (например, у CommBank любая положительная сумма считается доходом), поэтому в первой версии они траты не уменьшают. Это известное упрощение.
- **Пересчёт валют**: из `amount` и `currency` транзакции, по курсу на дату транзакции. Курс берётся из `ExchangeRate` с базой USD: последний курс на дату транзакции или раньше, так же как это уже делает `Transaction.save`. Формула: `amount / rate(USD→валюта транзакции) × rate(USD→целевая валюта)`, где rate для USD равен 1.
  - Поле `original_amount` для этого **не используется**: в нём не всегда USD (у переводов там KZT). У операций BCC с конвертацией `currency` хранит валюту покупки, `amount` хранит сумму покупки, а `original_amount` хранит списание в валюте счёта. Например, карта BCC USD в Австралии: `amount=-45.68 AUD`, `original_amount=-33.50 USD`. Для дашборда берётся сумма покупки, `amount` + `currency`.
  - Если курса нет совсем, транзакция в сумму не входит, а `summary` возвращает их число. Фронт показывает предупреждение «N транзакций без курса».
  - Трата с `amount = 0` (теоретически возможна, если у BCC пара валют без USD) считается так же, как «без курса»: в сумму не входит и попадает в тот же счётчик. В локальной базе на 24.10 таких нет.
  - Курсы за нужный период загружаются одним запросом, а не по запросу на транзакцию.
- **Периоды**: «сегодня» считается по часовому поясу дашборда, новая настройка `DASHBOARD_TIMEZONE`, по умолчанию `Australia/Brisbane`. Неделя с понедельника по сегодня, месяц календарный с 1-го по сегодня. «Прошлый месяц на ту же дату» означает с 1-го по тот же день прошлого месяца; если такого дня нет, берётся последний день месяца. `Transaction.date` хранит дату из выписки и сравнивается с этими границами как есть.
- **Категории**: траты сворачиваются к категории верхнего уровня, вверх по `parent_category`. Траты без категории идут в отдельную строку «Без категории».
- **Валюты в переключателе**: USD и все валюты, для которых есть курсы в `ExchangeRate`. По умолчанию AUD (настройка `DASHBOARD_DEFAULT_CURRENCY`). Выбор запоминается в браузере (`localStorage`).

### Статусы
- **Свежесть счёта**: считается **по счёту** (`Account`), а не по источнику выписок, потому что часть транзакций попадает без выписки. Например, у ANZ AUD все 6 транзакций внесены без выписки. Свежесть равна самой поздней `Transaction.date` по счёту.
  - Показываются только «живые» счета: с транзакциями за последние 180 дней. Старые счета (Halyk, Kaspi, Deniz, Ziraat, последние операции в 2023–2024 годах) не захламляют строку.
  - Зелёный: последней транзакции не больше 3 дней.
  - Оранжевый: 4–10 дней.
  - Красный: больше 10 дней.
  - Отдельно по каждому `BankSource` показывается последняя выписка, если она в статусе FAILED.
- **Курсы**: зелёный, если последний курс не старше `STALE_RATE_AFTER` (уже есть в `money/models.py`, 7 дней), иначе красный.
- **Без категории**: число трат без категории за текущий месяц. Оранжевый, если оно больше нуля.
- **Выписки**: FAILED и PENDING старше часа. Показываются красной меткой, только если такие есть.
- Пороги лежат константами в одном месте бэкенда, чтобы их легко было поменять.

### Изменение модели: флаг «не трата»
- Зачем: почти все парсеры помечают переводы между своими счетами как `expense`. CommBank считает тратой любую отрицательную сумму, BCC любое списание; настоящий `transfer` ставит только парсер FF. Без исключения дашборд посчитает такие переводы и оплаты карт тратами.
- В `ExpenseCategory` добавляется `is_spending = BooleanField(default=True)` с понятным `help_text` («Учитывать в тратах на дашборде») и одна миграция. Существующее поле `for_categorized` не трогаем: оно про другое, это список категорий для автокатегоризации.
- Флаг наследуется: транзакция исключается, если флаг снят у её категории или у любого предка по `parent_category`. Это нужно, потому что график всё равно сворачивает траты к верхнему уровню.
- Поле видно и редактируется в админке категорий.
- Категорию «Переводы между своими» владелец создаёт сам в админке и сам заводит для неё правила. Категории пользовательские (`user` FK), поэтому миграция данных не нужна.
- Исключённые траты на дашборде нигде не показываются. Если на них стоит посмотреть, их видно в админке по фильтру категории.

### Сборка и деплой
- **Разработка**: Vite dev server на `5173` проксирует `/api`, `/accounts`, `/admin` и `/static` на Django (`8000`). Cookie остаются на одном origin, CORS не нужен.
- **Прод**:
  - в `Dockerfile.prod` добавляется Node-стадия, которая собирает `frontend/` (`npm ci`, проверка типов, тесты, `npm run build`), а собранный `dist` копируется в итоговый образ;
  - при старте `web` раскладывает `dist` в общий volume, так же как сейчас `collectstatic` делает со статикой;
  - Caddy монтирует этот volume и отдаёт SPA, для неизвестных путей отвечает `index.html`. `/api/*`, `/admin/*`, `/accounts/*`, `/money/*` идут в `web:8000`, `/static/*` как сейчас.
- GitHub Actions (`deploy.yml`) уже собирает образ из `Dockerfile.prod`, поэтому фронт попадёт в деплой без новых шагов. Если сборка или тесты фронта падают, падает и сборка образа.

### Тесты бэкенда
Django `TestCase` в стиле существующих `money/tests.py`:
- пересчёт валют, включая USD, отсутствие курса и курс с более ранней даты;
- границы периодов;
- что переводы и доходы не попадают в траты;
- что траты с категорией «не трата», включая её подкатегории, не попадают в суммы и в график;
- сворачивание категорий;
- раскраска статусов;
- изоляция по пользователю;
- 401 без входа.
